# Контракт программного интерфейса

## 1. Выбор интерфейса

**Операция:** Авторизация пользователя.

**Тип интерфейса:** HTTP API (REST).

**Метод:** POST.

**Адрес:** /auth/login.

**Назначение:** Авторизация зарегистрированного
пользователя в системе BurnDo с использованием
электронной почты и пароля.

**Связанный пользовательский сценарий:**
US-1.1 — Как студент я хочу иметь возможность зарегистрироваться и авторизоваться в системе с использованием электронной почты и пароля, чтобы получить доступ к возможностям приложения.

**Связанное функциональное требование:**
FR-1.3 — Система должна предоставлять пользователям возможность авторизоваться с использованием адреса электронной почты и пароля.

## 2. Описание контракта

**2.1. Вызов операции**
Операция вызывается Frontend-приложением или другим HTTP-клиентом посредством POST-запроса.

Полный адрес при локальном запуске: http://localhost:8000/auth/login

Формат передаваемых данных: JSON (Content-Type: application/json).

Для авторизации предварительный вход в систему не требуется.

**2.2. Входные данные**
Операция принимает следующие параметры:
| Параметр | Тип данных | Обязательный | Ограничения |
|---|---|---|---|
| email| Строка | Да | Корректный адрес электронной почты |
| password | Строка | Да | От 1 до 128 символов |

Условия вызова:
- Пользователь должен быть зарегистрирован в системе.
- Email должен соответствовать адресу зарегистрированного пользователя.
- Пароль должен совпадать с сохранённым паролем пользователя.
- Удалённые аккаунты не могут пройти авторизацию.

**2.3. Результат успешного вызова**
При успешной авторизации операция возвращает HTTP 200 OK.

В теле ответа содержится JSON с информацией об аккаунте:
- id — идентификатор пользователя;
- name — имя пользователя;
- email — адрес электронной почты;
- role — роль пользователя;
- group_id — идентификатор учебной группы;
- group_name — название учебной группы;
- timezone — часовой пояс группы.

Дополнительно сервер устанавливает cookie burndo_session, содержащую токен сессии пользователя.

Параметры cookie:
- HttpOnly — включён;
- SameSite — lax;
- Secure — выключен по умолчанию;
- Срок действия — 14 дней при стандартных настройках проекта;
- Path — /.

Пример структуры успешного ответа:
```bash
{
    "id": 1,
    "name": "Иван Иванов",
    "email": "ivan@example.com",
    "role": "student",
    "group_id": 1,
    "group_name": "БПИ2302",
    "timezone": "Europe/Moscow"
}
```
Пароль пользователя в ответе не возвращается.

**2.4. Обработка ошибки**
Если пользователь вводит неправильный адрес электронной почты или пароль, операция возвращает HTTP 401 Unauthorized.

Формат ответа — JSON:
```bash
{
  "code": "authentication",
  "message": "Неверный email или пароль"
}
```
В этом случае авторизация не выполняется, а новая сессия не создаётся.

**2.5. Пример успешного вызова**
Запрос:
POST /auth/login HTTP/1.1
Host: localhost:8000
Content-Type: application/json
```bash
{
    "email": "student@example.com",
    "password": "student12345"
}
```
Ожидаемый результат: HTTP 200 OK.
Сервер возвращает информацию об аккаунте пользователя и устанавливает сессионную cookie burndo_session.

**2.6. Пример вызова с ошибкой**
Запрос:
POST /auth/login HTTP/1.1
Host: localhost:8000
Content-Type: application/json
```bash
{
    "email": "student@example.com",
    "password": "wrongpassword"
}
```
Ожидаемый результат: HTTP 401 Unauthorized.
```bash
{
    "code": "authentication",
    "message": "Неверный email или пароль"
}
```
Пользователь не проходит авторизацию, поскольку введённый пароль не совпадает с сохранённым.
